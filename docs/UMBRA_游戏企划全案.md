### 0.2 数值标记法（读表前必看）

本文每一个数字后面都跟着一个编号，格式为 `0.6 s（→T2）`。这不是装饰，是溯源：**没有编号的数字视为不可信。**

| 标记 | 含义 | 你能拿它做什么 |
|---|---|---|
| `（→T#）` | 真值表中的**定稿**值 | 可直接实现、可直接验收 |
| `待定（T9，草案：…）` | 真值表中的**草案**值，未经 playtest 验证 | **不得**当结论引用，不得作为排期依据 |
| `【内部】` | 项目自有结论，非外部事实 | 可引用，需说明是本项目判断 |
| `【A】/【B】/【C】` | 竞品数据的可信度分级：官方公开 / 三方转述 / 分析推断 | 【B】【C】需二次核实后用 |

### 0.3 一句话回答「这跟 Sqube Darkness 有什么不一样」

它是**位置型**潜行——站到光扫不到的地方；我们是**状态型**潜行——改变你此刻**是什么材质**。它是「躲」，我们是「演」。详述见 §4.3。

## 一 · 产品定义

### 1.1 参数包

| 参数 | 值 |
|---|---|
| 游戏类型 | 2D 横版 · **状态型潜行平台** + 结构轻肉鸽（无 Build、无局内成长） |
| 平台 | 浏览器纯前端单页，零依赖、零构建、零外部请求 |
| 目标玩家 | 核心玩家：偏好极简、高可读、**5–12 分钟一局**的网页 / 独立游戏玩家 |
| 开发周期 | 6 个月 / **26 周**（→T11-b） |
| 团队 | **7 人**（工程 5 / 美术 2），折合 **5.10 FTE**（→T11-c） |
| 总工作量 | **663 人日** = 已分配 495 + 缓冲 168（→T11-a） |
| 核心动词 | **停止**——全游戏只有一个。没有攻击、没有技能、没有道具 |

### 1.2 三条设计支柱

| # | 支柱 | 判据（用来砍功能，不是用来写宣传语） |
|---|---|---|
| **P1** | **动词只有一个：停止** | 任何新增操作，是否稀释「忍住不动」？是→砍 |
| **P2** | **玩家永远在演** | 反馈说的是「演得像不像」，还是「安不安全」？后者→改 |
| **P3** | **世界记得你** | 这个元素在玩家死过一次之后，会不一样吗？不会→它只是背景 |

> P2 是本文档里最容易被违反的一条。任何「安全提示」「危险预警」类设计，本质上都在把游戏从**表演**拉回**求生**，一律否决。

### 1.3 核心循环三层

| 层 | 时长量级 | 玩家在做什么 | 情绪目标 |
|---|---|---|---|
| **微观**（秒） | 1–3 s | 读灯的扇形、算它什么时候转开、忍住不动 | 屏息 |
| **中观**（单关） | 40–70 s（→T4，Demo 现状） | 在「必须移动」和「必须停下」之间反复切换 | 克制后的释放 |
| **宏观**（单局 / 跨局） | 3–6 min（→T4）／正式版 `待定（T9，草案：8–12 min）` | 判断哪些黑砖是真的、认出墙里上一轮的自己 | 认领一个身份 |

> **T9 的边界**：正式版节奏三值（单关 60–90 s / 单局 8–12 min / 5–7 房间每局）目前**三值不闭合**——按 5–7 房间 × 60–90 s 逐档复算得单局 [5.0, 10.5] min，与草案 8–12 min 不重合。原因是「单局」是否计入死亡重试、开场轮换、通关记忆演出尚未声明。**在 playtest 澄清口径之前，本全案任何排期与内容量判断都不依赖 T9**（详见 §9.3）。

## 二 · 核心机制

### 2.1 一句话说清「伪装」

贴住黑砖、**什么都不做**，0.08 s（→T1）后你会：

1. **摊平**成脚下那一格砖的形状（22×24 圆角方块 → 30×30 方角，四周各留 1 px）
2. **对色**到与砖完全一致（`#060606`，与砖的 ΔL\* 仅 1.65）
3. **闭眼**
4. **跳过全部光照判定**

一动就全部撤销——眼睛睁开，那一刻它就是一个站在光里的黑方块。

### 2.2 为什么是「状态」而不是「位置」

这是整个项目最重要的一次概念收敛，也是三次返工换来的。

| | 位置型潜行（Sqube Darkness 等） | **状态型潜行（本作）** |
|---|---|---|
| 玩家在管理什么 | 自己的**坐标** | 自己的**材质** |
| 安全区在哪 | 地图上，光扫不到的地方 | 地图上，黑砖所在的地方——但只有你**变成砖**才安全 |
| 失败长什么样 | 被光照到 | **被光照到「还活着」** |
| 核心张力 | 空间够不够 | **忍不忍得住** |

**为什么不能做成「融入」**：融入是个空间隐喻（你进入了某个东西），玩家会本能地去找「可以融入的地方」——那就退化成位置型潜行了，只是换了个说法。伪装是**材质**隐喻：你不是进入砖，你是**承认自己本来就是砖**。这句话直接通向叙事（§3.3）。

### 2.3 判定链（可实现级）

| 序 | 条件 | 结果 | 数值 |
|---|---|---|---|
| 1 | 脚下或身侧有实体黑砖 | 允许伪装 | — |
| 2 | 水平速度 < 34 px/s 且持续 0.08 s | 进入伪装态 | →T1 |
| 3 | 伪装态下任意输入（含 1 px 位移） | 立即解除，眼睛睁开 | 瞬时 |
| 4 | 暴露值 > 0 | 开始累积 | — |
| 5 | 暴露值满 | 烧穿 | 0.6 s（→T2） |
| 6 | 暴露值回落 | 恢复 | 0.55 s；伪装状态下 ×3（→T2） |
| 7 | 伪装状态下被光扫过 | **完全无效果** | — |
| 8 | 站在灰硬砖 / 空中 / 尖刺上 | **不可伪装** | — |

> 边界 8 是整套关卡语法的地基：**所有安全都必须靠跳跃抵达，不能趴在出生点原地无敌。**

### 2.4 伪装不像伪装的根因，以及怎么修的

第一版 Demo 里伪装「看起来就是不像」，玩家一眼就能认出那里有个方块。根因不在动画，在**材质**：

> 黑砖原本是一条**无缝的黑色带子**。任何方块站上去，物理上必然是凸起。

解法是反过来做：**先让墙可数出格子**。

- 黑砖加 1 px 竖缝（`rgba(255,255,255,.05)`）+ 顶边两端各留 2 px 断口
- 玩家伪装时摊成 30×30、四周各 1 px 内缩，正好填进那一格
- 只剩一条 9% ± 2% 的白描边在呼吸（`0.09 + 0.02·sin`，`game.js:1513`）——这是他**能找到自己**的唯一破绽，而不是暴露给敌人的破绽

> **衍生规则（写进美术铁律）**：任何新增地形只要破坏「能数出格子」这件事，伪装就不成立。这条比任何风格偏好都优先。

### 2.5 光：一个有意识的看守

灯不是障碍物，是**角色**。它有瞳孔、会朝视线方向偏移看、会在你消失的地方愣住。

| 状态 | 触发 | 表现 | 数值 |
|---|---|---|---|
| 巡视 PATROL | 默认 | 扇形扫动，摆幅 ±0.28–0.42 rad，射程 460–640 px | — |
| **愣住 CURIOUS** | 你在被照到的瞬间完成伪装 | **完全静止** 3.6 s，扇宽收窄**至**原扇宽的 82%，再用 0.9 s 平滑归位 | →T3 |
| 归位 | 愣住结束 | 沿缓动轨道滑回原摆动区间 | 0.9 s（→T3） |

**为什么是「静止」而不是「抖动」**：静止像愣住，抖动像故障。这是全片唯一一处「敌人有情绪」的表演，滥用就失效。

**为什么这个停顿是玩法而不是特效**：它给了你一个可计时的窗口——灯在找，但它已经找不到了。你最好别急着起身。

### 2.6 门：不是出口，是轮换

| 常规平台游戏 | 本作 |
|---|---|
| 门是终点，通关即离开 | 门是**轮换**：走出去的人变成下一局的灯 |
| 墙是背景 | 墙里那些**闭眼轮廓**刻痕，都是上一轮的你 |
| 死亡是清零 | 死亡在地图上**留下痕迹**（§3.3） |

这一条是「目的」这个问题的答案。玩家在试玩时最常问的是「我为什么要往前走？我只知道攒星星、到传送门」。答案必须由规则本身体现，不能靠文字解释：

> **你不是在逃出去，你是在换一个位置继续当墙。**

## 三 · 循环与节奏

### 3.1 单局结构

```
开场轮换（灯闭眼 → 砖睁眼，2.4 s）
   ↓
房间 1 ─ 房间 2 ─ … ─ 房间 N   ← 手工房间池随机抽取，灯相位随机
   ↓                    ↓
 死亡 → 烧痕留在原地    通关 → 记忆演出（本局三个事件）
   ↓                    ↓
重开本局（痕迹保留）      门 → 下一轮（你变成灯）
```

### 3.2 为什么是「结构轻肉鸽」而不是「肉鸽」

| 维度 | 有 Build 的肉鸽 | **本作** |
|---|---|---|
| 局内成长 | 有（捡装备、叠数值） | **零**。整局能力不变 |
| 随机的是什么 | 掉落、敌人、Build 组合 | **房间排列 + 灯的相位** |
| 重玩的动机 | 换一个 Build 试试 | **换一种走法，看世界记不记得** |
| 失败后带走什么 | 永久解锁 | **地图上的痕迹** |

> 不做 Build 是刻意的：一旦有 Build，「忍住不动」就会被「我的 Build 能不能硬扛」稀释，P1 直接破。随机化的目的不是多样性，是**让每一局的「忍住」都需要重新计算**。

### 3.3 记忆：玩家记得住的只有三件事

这一节是本项目返工次数最多的部分，值得写清失败的两次。

**第一次尝试**：通关后播 5 张抽象定格。→ **看不懂**。玩家不知道那些画面和自己有什么关系。
**第二次尝试**：回放整条真实轨迹。→ **记不住**。玩家记不住上一把自己是怎么走的，回放对他没有意义。
**定稿**：只留**三个事件**，且每个事件都兑换成**手感**。

| 事件 | 触发 | 墙上留下什么 | 手感兑现（下一局） |
|---|---|---|---|
| **死过** DEATH | 在某一格被烧穿 | 漂白圆印 | 走到那里**更难冷静**（伪装变慢） |
| **憋过** HOLD | 单局内静止最久的位置 | 闭眼砖屑刻线 | 走到那里**伪装更快**（身体先认出来） |
| **冲过** DASH | 冲刺穿过光区的落点 | 一道短线 | 记录你曾经敢 |

**关键技术约束**：痕迹必须吸附到**最近实体砖格**（断崖列向左右最多 6 格兜底），否则会浮空、或看起来像 UI 按钮。视觉上统一用「砖面刻痕」（顶边断口 + 两道闭眼刻线），**不画独立方框**。

**深度系统**：`save.depth` 0–5，每关 4–5 个记忆位点，全作 22 处（→T8）。随关卡推进逐步显露更早的记忆——不是收集品，是**世界逐渐承认你回来过**。

### 3.4 时长

| 口径 | 值 | 状态 |
|---|---|---|
| 单关（Demo 现状） | 40–70 s | 定稿（→T4，现状基线） |
| 单局（Demo 现状） | 3–6 min | 定稿（→T4，现状基线） |
| 关卡数（Demo 现状） | 5 关 | 定稿（→T4） |
| 单关（正式版） | `待定（T9，草案：60–90 s）` | 草案 |
| 单局（正式版） | `待定（T9，草案：8–12 min）` | 草案 |
| 房间数/局（正式版） | `待定（T9，草案：5–7 房间/局）` | 草案 |

> **T4 的「关」与 T9 的「房间」不是同一单位，不得混用。** T4 是 5 关线性 Demo；正式版是无限轮 + 房间池重排。若按 T4 的「5 关」去实现正式版，会做出一个五关**线性**游戏而不是肉鸽——这是本项目最容易犯的转译错误。

## 四 · 竞品分析

> 完整拆解见 `GDD_竞品拆解.md`（四款对标逐维度九行表 + 20 条来源清单）。本节只留结论与**我们明确不做的事**。

### 4.1 四款对标：一句话各自的位置

| 作品 | 它与「光」的关系 | 核心动词 | 循环结构 | 死之后 |
|---|---|---|---|---|
| **Sqube Darkness**（网页版 2026-04，→T12-a） | 位置：躲进阴影 | 跑 / 跳 / 躲 / 冲刺 | 一次性高分挑战 | 重开，不留痕迹 |
| **Dead Cells**（2018-08，→T12-g） | 无关（霓虹只是氛围） | 砍 / 滚 / 死 / 解锁 | Rogue-lite + 永久解锁 | 失去局内进度，保留解锁 |
| **Limbo / Inside**（2010 / 2016，→T12-k） | 视觉语法 | 走 / 跳 / 推 / 试错 | 线性一次性通关 | 检查点重试 |
| **Closure**（2009 Flash / 2012） | 工具：照到才存在 | 携光 / 照亮 / 通过 | 线性关卡集 | 重开本关 |
| **UMBRA** | **对手：骗过有意识的看守** | **停止** | **结构轻肉鸽、局内零成长** | **留烧痕 / 轮廓，跨轮累积** |

四款里有两款（Sqube、Closure）验证了「网页 + 极简几何 + 短重试」这条路能跨端长跑——Sqube 从 2021 手游走到 2026 网页版，Closure 从 2009 Flash 走到 2012 多平台。**这是美术路线抗疲劳的外部证据，也是我们选几何而非手绘的市场侧理由之一。**

### 4.2 三个空位

| 空位 | 邻近位置有谁，但没占住 |
|---|---|
| **A · 把「伪装」做成状态机**（而非位置 / 隐身 / 显形） | Sqube 是「站到光扫不到的地方」；Closure 是「光决定地形是否存在」。**无一款把「你此刻是什么材质」当作唯一判定** |
| **B · 让「光」成为有意志、会迟疑的对手** | Sqube 的光是 deadly lights（机械致命）；Closure 的光是玩家的工具；Playdead 的光是氛围。「灯会因你消失而愣住」未被占据（→T3） |
| **C · 无文字 + 短局 + 跨轮世界记忆，三者同时成立** | Dead Cells 有循环但靠物品描述承载记忆；Playdead 无文字但线性一次性；Sqube 短局但重开即忘 |

> **空位 A 的成立条件（必须写进对外答辩口径）**：同 IP 手游版的商店文案已出现 "a black cube that can fit right in the environment" 与 "watchful Eyes"（→T12-p · W3）。因此**不得声称「从未有人做过」**，只能主张：**在「浏览器短局 + 以状态判定为核心 + 失败痕迹跨轮累积」这个组合上，未见于本次四款对标。** 措辞收窄后仍成立，且一句话反驳不掉。

### 4.3 差异化到底差在哪：机制语义与反馈深度

对外不要说「我们有眼睛、他们没有」——这种「有无之别」一句商店文案就能推翻。准确的说法是**同一件事被做成了两种东西**：

| | 竞品把「眼睛」做成 | 我们把「眼睛」做成 |
|---|---|---|
| 本体 | 巡逻的致命怪 | **有情绪的看守** |
| 对玩家的意义 | 要绕开的障碍 | 要被骗过的对象 |
| 反馈深度 | 你若被看见 → 死 | 你若**在它眼前消失** → **它会愣住 3.6 s（→T3）** |

同理，「贴住环境」在竞品那里是**位置躲藏**（fit in the environment = 躲进去），在我们这里是**材质同化 → 判定跳过**的闭环。**差的是语义层级与反馈深度，不是有无。**

### 4.4 我们明确不做的事（不模仿清单）

| 不做 | 原因 |
|---|---|
| 冲刺无敌帧 | 会稀释「忍住不动」（P1） |
| 多技能键 / 道具栏 | 同上；动词只能有一个 |
| 伪装时贴墙缓慢移动 | 把「状态」降级成「姿态」，张力消失 |
| 安全提示条 / 危险预警 UI | 把「表演」拉回「求生」（P2） |
| 局内数值成长 / Build | 会让「我的 Build 能不能硬扛」替代「我忍不忍得住」 |
| 角色皮肤 / 局外解锁外观 | 「每关都是同一个你」（P3），外观一变叙事就散 |
| 游戏内任何字符串 | 零文字铁律（§5） |

## 五 · 无文字叙事

### 5.1 铁律

**游戏内零字符串。** 没有教程、没有提示、没有 UI 文案、没有对白。允许存在的「字」只有两种：标题页的键位箭头（`← → ↑ ≫`，属符号不属文案）和浏览器标签页标题。

### 5.2 五种替代通道

删掉文字不是省事，是**把表达成本转移到别处**。本项目用五条通道承接：

| 通道 | 承担什么 | 具体形式 |
|---|---|---|
| **形状** | 操作与进度 | 键帽图标、关卡点、碎片插座、暴露条、状态点（全部图形） |
| **静态线索** | 第一次「我该停下」 | 被光扫到时，灯下那块砖浮出**闭眼轮廓**——不演示、不说教，只呈现「有人这么干过」 |
| **烧痕** | 失败是可累积的 | 漂白圆印、砖屑刻线、短线（§3.3） |
| **门上的插座** | 我离目标还有多远 | 碎片进度**直接长在门上**，撞锁时闪烁 |
| **状态点** | 我现在安不安全 | 实心 = 暴露，空心 = 已伪装 |

### 5.3 引导必须遵守「目的 → 过程 → 结果」

这一条是三次返工的核心教训。**任何引导都必须先让玩家产生目的，再展示过程，最后给出结果**——顺序颠倒就变成说明书。

| 错误做法 | 为什么错 |
|---|---|
| 开局就在玩家面前放一个残影演示伪装 | 玩家还没有「我要躲光」的目的，演示对他只是动画 |
| 预置一排「正确路线」的遗迹 | 只有结果、没有过程，玩家不知道那是怎么发生的 |
| **（定稿）在玩家第一次被光扫到时**，让灯下那块砖浮出闭眼轮廓 | 此刻他**刚有了目的**（别被照到），线索才有意义：原来可以变成砖 |

> **推论**：所有引导都必须**事件触发**，不能关卡预设。没有触发事件的地方，宁可不引导。

### 5.4 失败信号的定义

无文字游戏最大的风险不是「没有信息」，而是「玩家不知道自己做错了」。本项目把「看不懂」定义为**必须处置的失败**，而非留白：

| 玩家状态 | 判定 | 处置 |
|---|---|---|
| 「我不知道我在干嘛」 | **失败**，必须修场景 | 检查该处是否有「目的 → 过程 → 结果」的缺口 |
| 「我不知道我为什么死了」 | **失败**，必须加因果 | 补烧穿前的可视预兆（0.6 s 灼烧条 + 负片闪，→T2） |
| 「我大概知道要停下」 | **通过** | — |

> 与 Playdead 的区别：他们拒绝确认解读，沉默是主题；我们把猜谜视为**失败信号**。**同样零文字，目的完全不同——他们要留白，我们要因果被看懂。**

## 六 · 美术

> 完整清单见 `GDD_美术清单.md`（39 项 / 70 张逐项规格 + 13 条 AI 提示词）、规范页 `art/style-guide.html` v3.1。

### 6.1 风格定义与三条铁律

**低明度单色几何 + 印刷砌块质感 + 一种被叫作「光」的材料。**
世界是灰的，障碍与同类都是黑的，光是唯一允许发亮的东西；全部信息由明度与形状承担，没有色相，没有纹理噪声，没有一个字。

| # | 铁律 | 可验收判据 |
|---|---|---|
| **R1** | 只有明度，没有色相 | 全片不出现色相偏移；新元素必须落进既有 6 条明度带（L\* 0–5.43 / 6.32 / 26.37 / 30.31–42.14 / 35.74 / 92.60–100） |
| **R2** | 伪装靠网格与缝，不靠明度差 | 玩家 `#000000`（L\*=0）与砖 `#060606`（L\*=1.65）的 ΔL\* 仅 **1.65**——可分辨性 100% 由 1 px 竖缝、2 px 顶边断口、尺寸差、9% 描边呼吸承担 |
| **R3** | 光独享发光权 | 除光与碎片外一切为 1–2 px 硬边；无外发光、无投影、无圆角卡片、无镜面高光 |

### 6.2 为什么不是手绘（三条，按重要性）

1. **机制一致性是硬约束，不是审美偏好。** 伪装成立的前提是玩家与砖**逐像素同色**，该差值已被压到 ΔL\*=1.65。手绘纹理自带笔触与明度抖动，会把这个余量直接吃掉——玩家「永远差一点点、永远露馅」。这是机制漏洞，不是画得不好。
2. **判据是 0.3 秒可读性。** 玩家要在半秒内判断「这块黑我能不能钻进去」。手绘的价值来自细节密度，而细节密度在这个判据下是**负资产**。
3. **预算必须押在光上。** 本作唯一会「表演」的是灯的三态与三层后期；砖与地形应是「改数据」而非「重画」。省下的工时全部转入光的表演。

### 6.3 资源总量（→T10）

| 类别 | 项数 | 张数 | 生成方式 |
|---|---:|---:|---|
| 角色（玩家三态 + 死亡消散） | 4 | 4 | 纯代码绘制 |
| 灯（虹膜两态 / 锥光 / 激光三态） | 4 | 7 | 纯代码绘制（离屏光照层） |
| 地形材质 | 5 | 6 | 纯代码绘制 |
| 门 / 传送 | 4 | 8 | 纯代码绘制 |
| 记忆演出与过场 | 6 | 9 | 纯代码绘制 |
| 粒子与后期 | 6 | 9 | 程序化生成 + 1 张位图 |
| HUD 与界面符号 | 6 | 21 | 纯代码 / DOM+CSS |
| 宣传物（商店页 / 封面） | 4 | 6 | AI 生成 + 人工合成 |
| **合计** | **39 项** | **70 张** | **70 张中仅 `A-24` 为位图，且由 `ensureNoise()` 运行期生成 → 包体内新增位图 0 B** |

**计数口径**：1 项 = 一条可下单的资源条目（唯一编号 `A-xx`）；1 张 = 一个可独立渲染/对齐/导出的画布产物。**序列帧动画帧数 = 0 帧/项**——本作没有逐帧动画，全部状态过渡由参数化插值驱动（指数逼近 / 线性 / 正弦）。

> **项数为什么比通用清单多**：零文字游戏的 HUD 与记忆符号是唯一通信通道，必须逐态拆成可单独对齐的条目；且 8 类里有 5 个全屏后期/离屏光照层的混合模式互不相同（`screen` / `multiply` / `difference` / `source-over`），不可合并。

### 6.4 AI 提示词策略

**13 条提示词覆盖 14 项资源，24 项明确禁止 AI 生成**（→T10-d）。

- 共用一段 **style token 块**作为风格锚点（低明度单色几何、印刷砌块、无纹理、无外发光）
- 逐条给正向 + 负向 + 宽高比参数，编号与 `A-xx` 对应
- **禁止 AI 生成的**包括：HUD 图标、需逐像素对齐 32 px 网格的砖块、路径与碰撞相关的任何视觉——它们必须由代码参数化生成，否则无法保证「一格一砖」的对齐

### 6.5 抗疲劳：靠约束，不靠细节

长时间游玩不厌倦，不是因为画得细，而是因为**画面里没有会疲劳的东西**：

| 手段 | 参数 |
|---|---|
| 静态颗粒层 | 128×128 灰度 234–255，`multiply`——把纯色大块压成「有颗粒的材质」，是整套单色美学的底噪 |
| 世界呼吸 | 24 s 周期，白侧 +5% / 黑侧 −7%（**非对称**，`game.js:1147–1153`）——对抗静态画面的习惯化 |
| 明度纪律 | 同一屏内不超过 3 级明度阶 |
| 零色相 | 没有会「看腻」的强调色 |

## 七 · 技术方案

> 完整方案见 `GDD_技术方案.md`（9 节 / 850 行，含逐帧渲染顺序 26 步、三档逐档复算、11 条风险）。

### 7.1 技术选型：维持运行时栈，只重构源码（A′）

**结论：不换引擎、不引构建框架、不迁移 WebGL。** 运行时 100% 不变——仍零依赖、零构建、零外部请求、`file://` 可跑、产物仍是单文件；只把**源码**拆成 10 个模块，用约 60 行的 `tools/build.js` 拼接。

| 路线 | 包体 | 首帧代价 | 6 个月维护成本 | 判断 |
|---|---|---|---|---|
| **A′ 维持 Canvas2D + 源码模块化** | 发布口径 ≈ 88.9 KB | 0 | 低（现有 82 断言可直接复用） | **采用** |
| B 引入 Vite + ES Module | +构建链 | 需打包/拆包 | 中；**失去 `file://` 直开能力** | 否 |
| C 迁移 WebGL | 引擎或手写 GL 层 | **+80–250 ms 着色器编译** | 高；渲染代码增 3–5 倍，还要处理上下文丢失 | 否 |

**一句话理由**：现有 5 灯 DDA 每帧 14.4 ms / 16.7 ms 预算，**性能不是瓶颈**。换 WebGL 是为了解决一个本项目没有的问题，却要付出首帧、上下文丢失、三倍渲染代码三项代价。

### 7.2 渲染管线

逐帧顺序（`render()` 真实顺序，共 26 步，摘主干）：

```
清屏 → 背景渐变 → 世界层瓦片（≤561 格 × ≤4 fillRect）
  → 实体与装饰（碎片/门/玩家/尖刺/烧痕/波）
  → 粒子（arc + lighter）
  → 光照离屏层：DDA 射线生成可见性扇形多边形 → 逐灯填充 → screen 合成主画布
  → 静态噪点（multiply）→ 世界呼吸 → 暴露暗角 → 方向闪
  → 曝光负片（difference，烧穿时）→ HUD DOM 更新（60 ms 节流）
```

**光照是唯一的重活**：4 盏锥光 ×130 条 + 1 盏点光 ×170 条 = **690 条射线**，均 18 步 ≈ 12,420 次格子步进。

> **同屏锥灯上限 ≤ 7 盏（桌面档）**——按拐点公式 `n ≤ (16.7 − 基底) ÷ 单盏成本` 反算。这是设计侧的硬约束：关卡里放第 8 盏灯，就要先砍别的东西。

### 7.3 性能预算（三档逐档复算，不假设等比缩放）

| 环节 | 桌面 DPR2 | 中端 DPR1.5 | 低端 DPR1 + 降级 |
|---|---:|---:|---:|
| 逻辑 `step()` ×2（120 Hz） | 0.5 | 0.5 | 0.5 |
| 光照 DDA 射线 | 2.6 | 2.6 | 1.3（射线减半） |
| 光照层多边形填充 | 1.8 | 1.0 | 0.45（层降 480×272） |
| 世界层瓦片 | 2.2 | 1.6 | 0.9 |
| 实体与装饰 | 1.0 | 0.9 | 0.5 |
| 粒子 | 0.4 | 0.3 | 0（关闭） |
| `screen` 合成 | 2.0 | 1.1 | 0.5 |
| 噪点 `multiply` | 1.2 | 0.7 | 0（关闭） |
| 后期 4 层 | 2.0 | 1.1 | 0.5（合并为 1 层烘焙暗角） |
| HUD + 呈现 | 0.7 | 0.6 | 0.5 |
| **合计** | **14.4 ms** | **10.4 ms** | **5.15 ms** |
| 预算（60 fps） | 16.7 | 16.7 | 16.7 |
| **余量** | 2.3 ms（13.8%） | 6.3 ms | 11.55 ms |

**全档位统一承诺 60 fps（p95 ≤ 16.7 ms）**。档位差异体现在**降级开关的组合**，不体现在承诺值上。降级双阈值：软降 p95 > 16.7 ms 持续 180 帧 → 降一档；硬降单帧 > 22.2 ms 连续 120 帧 → 立即降；回升 p95 < 13 ms 持续 600 帧 → 升档。

### 7.4 内存预算

| 项 | 桌面 | 中端 | 低端 | 与 DPR 的关系 |
|---|---:|---:|---:|---|
| 主画布后备 | 7.97 | 4.48 | 1.99 | ∝ DPR² |
| 光照离屏 | 7.97 | 4.48 | 0.50 | 低端降半分辨率 |
| 显示合成层 | 7.97 | 4.48 | 1.99 | ∝ DPR² |
| 噪点 + 关卡 + 粒子 | 0.18 | 0.18 | 0.03 | 基本无关 |
| **WebAudio（噪声 buffer + 节点）** | 4.37 | 4.37 | 4.37 | **定额** |
| **JS 堆** | 12.00 | 10.00 | 8.00 | 上限随档收紧 |
| **合计（MiB）** | **40.46** | **27.99** | **16.88** | 逐项加总 |
| 上限（MB → MiB 折算） | 76.29 | 57.22 | 38.15 | 80 / 60 / 40 MB |
| **占用率** | **53.0%** | **48.9%** | **44.2%** | 用量 ÷ 上限 |

> **一个必须写在纸上的反直觉点**：低端档帧预算降了 62%（14.4→5.15 ms），但内存只降 58.3%（40.46→16.88 MiB）。因为 **WebAudio 4.37 + JS 堆 8.00 = 12.37 MiB 是与像素数无关的定额**，占低端档 73.3%。**「降档一定更省」是错的假设，三档必须各自复算。**

### 7.5 包体预算：把「剥离」变成硬约束（→T13）

| 口径 | 值 | 结论 |
|---|---:|---|
| 现状源码（三文件） | 88,603 B（→T6） | gzip 后 25,205 B |
| 剥离后 `game.js` | 71,650 B（实测） | 剥掉 6,832 B = 8.7% |
| **发布口径合计（中位）** | **88,900 B** | 余 11,100 B，**合规** |
| 发布口径（悲观） | 89,972 B | 余 10,028 B，**合规** |
| 源码口径（不剥离） | 115,243 B | **超 100 KB 上限 15.2%** |
| **gzip 预算** | **≤ 28,672 B（28 KiB）** | 基线 21,474 B，约可容 13 个房间 |

**因此 `--strip` 从「可选开关」升级为发布构建的强制步骤**，并加两条 CI 断言：产物 raw ≤ 100,000 B、产物内不含整行 `//`。

> 这一节是本项目最容易出事的地方。开发态永远看不出问题（源码 115 KB 也能跑），只有发布那一刻才会发现超线——所以必须由 CI 拦，不能靠人记。

### 7.6 【裁决】零外部请求 vs 门户 SDK 广告分成

**冲突的准确表述**：门户变现要求嵌入平台 SDK（外部脚本 + 运行时广告调用），而本作的产品承诺是「零依赖、零构建、**零外部请求**」。SDK 必然破这条，且会接管启动流程。

**裁决：采用方案 ③「双构建产物：干净版 + 门户版」，且默认交付物仍是零外部请求的干净版。**

| 维度 | ① 纯自托管 | ② 单产物挂 SDK | **③ 双产物** |
|---|---|---|---|
| 外部请求（干净版 / 门户版） | 0 / — | 1 + N | **0 / 1 + N** |
| 包体变化 | 0 | +100–300 KB，且主产物被污染 | **0 / +100–300 KB** |
| 首帧影响 | 0 | 4G 首访 +180–350 ms | **0 / 同上** |
| 6 个月返工 | 0 人日 | **26–34 人日** | **18–22 人日** |
| 对约束的影响 | 不改 | **永久失去零请求** | **主交付不改** |

三条理由，按权重：

1. **主交付的风险必须隔离。** `file://` 双击即玩、零请求、零文字，是它能在 itch / 邮件 / 微信 / U 盘里被随手点开的**全部前提**。方案 ② 用一个不可控的第三方脚本换掉这个前提，而 SDK 会在首屏塞进**全作唯一的文字**——这是叙事层面的破口，不只是技术层面的。
2. **③ 的返工量比 ② 低 30% 以上，且是纯增量。** 干净版代码零改动，门户版只是一个额外的 manifest + 注入头。
3. **③ 保留两条腿走路。** 门户分成条款本身是「待核实」（→T12-f），把发行全押在未核实费率上不理性；而条款明确「非独家、多平台发行不影响分成资格」，先自托管后补门户版在商务上完全合法。

**触发改向的条件（触发即改，不需再议）**

| 条件 | 改向 |
|---|---|
| 商务确认「门户为唯一渠道且首发日即变现」 | → ②，放弃零请求约束，M5 改为门户版单产物 |
| SDK 实测 EXT-01 > 300 KB 或 EXT-02 > 500 ms | → ①，门户版不立项 |
| 门户审核拒绝零文字游戏中的 SDK 广告弹窗 | → ①，记录审核原文存档 |
| M4 结束仍无变现意向 | → 默认落 ①，18–22 人日返还缓冲池 |

> **需产品方追加确认**：本裁决不修改「零外部请求」这条约束（干净版仍 0 请求），但**交付物从 1 个变 1+1 个，属范围变更**。门户版一旦立项，连带影响：内存 +4–8 MiB、首帧 +180–350 ms、包体破 100 KB 上限。本条需产品方明示同意后方可进入 M5 的门户版目标。

### 7.7 音频：全程序化，零音频文件

WebAudio 合成，常驻 14 个节点，噪声 buffer 48 kHz × 2 s × Float32 = 384 KB。**音频文件体积 = 0 B**。这不仅是省体积——它让「闭眼闷音」（lowpass 620 Hz）可以随状态连续调制，而不是切一段预录素材。

### 9.3 playtest：T9 的闭合路径

**T9 三值目前不闭合，必须先补口径再验证。** 顺序不能颠倒：

1. **先声明「单局」口径**：是否计入死亡重试、开场轮换、通关记忆演出？
2. **再逐档复算**：5 / 6 / 7 房间 × 单关 60 / 90 s，六格全算（**禁止只算一档、禁止「高档达标低档肯定更低」的假设**）
3. **再定稿**：区间闭合后方可提请把 T9 从 `草案` 升为 `定稿`

**观察维度**（不含阈值，阈值由 playtest 后定）：

| 维度 | 观察什么 |
|---|---|

| 首次主动停下时间 | 从开局到第一次有效伪装 |
| 目的读出率 | 能否不靠文字说出「门是轮换」 |
| 循环重玩动机 | 死过一次后是否主动重开 |
| **网页短会话兼容性** | 8–12 min 的单局在「5 分钟就来一局」的平台上是否出现中途流失 |
